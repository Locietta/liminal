# Context, Role, and Agent Architecture

Status: proposed  
Date: 2026-08-06

## Summary

Liminal should treat three concepts as separate:

1. A **message role** is a provider protocol concept. It identifies the authority or speaker of one item in a model request: `system`, `developer`, `user`, or `assistant`.
2. An **agent profile** is Liminal configuration. It describes an agent's purpose, instructions, model preferences, tools, and context policy.
3. A **context view** is the temporary, provider-specific projection of session state selected for one model call.

An agent is not represented by an `assistant` message. Model-generated conversation turns are represented by `assistant`; instructions that define the agent are represented by `developer` or by the closest provider-native instruction mechanism.

Liminal's current OpenAI behavior follows this rule. It sends the default coding-assistant prompt as a `developer` message and records generated text as `assistant`. Changing generated turns to `developer` would incorrectly promote previous model output into high-priority instructions.

The larger architectural change is to stop using provider message roles as the primary session model. Liminal should retain a provider-neutral, append-only session log and construct a bounded context view for every request. This creates a clean path to automatic compaction, branching, reusable agent profiles, and optional child agents without requiring child-agent execution now.

## Implementation status

- Phase 1 is complete: instructions have semantic authority and provenance, agent conversation is separate from instructions, and each provider call uses an inspectable context manifest.
- Phase 2 is in progress: the agent now owns an in-memory semantic session log with session and entry IDs, parent links, an active leaf, branch projection, and append-only compaction checkpoints.
- Durable session storage and recovery remain to complete Phase 2.
- Context budgets, automatic compaction, agent profiles, and child-agent execution remain future phases.

## Goals

- Preserve the intended instruction hierarchy across providers.
- Keep agent configuration distinct from conversation messages.
- Make every model request a deliberate, inspectable context projection.
- Support long-running sessions through token accounting and automatic compaction.
- Preserve provider-native reasoning and tool items when they are needed for continuation.
- Allow a root agent and future child agents to use the same runtime abstraction.
- Keep the initial implementation lightweight and avoid building orchestration before it is needed.

## Non-goals

- Implement child-agent spawning or supervision in the first phases.
- Create a universal representation of private reasoning across providers.
- Guarantee that provider-native opaque items can be moved between providers.
- Add compatibility layers for the current in-memory history API.
- Put all potentially useful context into every request.

## Terminology

### Message role

A wire-protocol label used when lowering context to a provider request. It must not double as an agent type or profile name.

### Instruction authority

The precedence of a Liminal-owned instruction source. The initial authority classes are:

- **Runtime**: Liminal's platform and safety contract.
- **Application**: the selected agent profile and product behavior.
- **Project**: trusted repository instructions such as `AGENTS.md`.
- **Task**: the user's request and subsequent clarification.

These names are internal semantics, not promises that every provider has four matching wire roles. Provider adapters serialize them using the strongest faithful representation available.

### Agent profile

Reusable configuration describing what an agent is intended to do. A profile is not a message and is not mutable session state.

### Agent instance

A running use of an agent profile, attached to a session branch and execution state. The user-facing main agent is the root instance: the same type as a future child instance, but with no parent.

### Session log

The durable, provider-neutral record of user input, generated output, tool activity, summaries, and provider-native continuation data.

### Context view

The bounded selection and rendering of instructions, session entries, tools, and retrieved material used for one model call. It is derived state and is never the source of truth.

## Findings

### OpenAI roles

OpenAI's guidance defines the roles as follows:

- `developer` contains application rules and business logic and takes precedence over `user`.
- `user` contains end-user input.
- `assistant` contains messages generated by the model.

The Responses API accepts high-level guidance either through top-level `instructions` or compatible message items. Top-level `instructions` applies only to the current response and is not automatically carried forward with `previous_response_id`. When an application manages the transcript itself, explicit developer message items are a valid representation.

Therefore:

- The agent profile's governing prompt belongs in `developer` or top-level `instructions`.
- A user's task belongs in `user`.
- The agent's prior generated answer belongs in `assistant`.
- Tool calls, tool results, reasoning items, and compaction items should use their typed Responses API forms rather than being disguised as chat messages.

There is no evidence that representing generated output as `assistant` causes a performance downgrade. It is the provider's intended representation. Representing it as `developer` would change its meaning and authority and is likely to harm instruction following.

Liminal currently does the correct thing in `provider::History`: the default agent instruction is appended as `DEVELOPER`, while model output is appended as `ASSISTANT`. The OpenAI adapter also emits those roles directly. This behavior should be protected by tests.

### OpenAI `instructions` versus developer items

Liminal currently sends its manually managed history through Responses `input`, including explicit developer messages, instead of rebuilding top-level `instructions` on every call. That is a sound default because it:

- keeps instruction entries explicit in the transcript projection;
- works with manual, stateless response replay;
- maps cleanly from the provider-neutral instruction stack; and
- avoids relying on request-scoped instruction carry-over.

The context builder may later choose top-level `instructions` as an OpenAI-specific optimization, but only if equivalence is verified for the models Liminal supports. The architecture must not rely on an unverified quality or caching advantage from either representation.

### Anthropic roles

Anthropic's Messages API uses `user` and `assistant` conversation turns and a top-level `system` parameter for system instructions. It does not have a direct, generally portable equivalent of OpenAI's `developer` role.

Liminal currently collects system and developer entries into Anthropic's system prompt and maps generated history to `assistant`. This is the appropriate portability strategy. The adapter should preserve the order and provenance of internal instruction blocks, while recognizing that the provider does not natively reproduce every OpenAI authority level.

Some current Claude models support additional mid-conversation system messages, but Liminal should not make its base session semantics depend on a model-specific feature. Such capabilities can be added to provider/model metadata and selected during lowering.

### Anthropic's context-engineering guidance

Anthropic reports that it removed more than 80% of the Claude Code system prompt for its Claude 5 generation without a measurable loss on coding evaluations. Its recommendations point toward a smaller stable prompt and better context architecture:

- Give advanced models room to exercise judgment instead of accumulating absolute rules.
- Put behavior close to its owner: tool behavior in tool schemas and specialized workflows in skills.
- Prefer progressive disclosure over loading all documentation up front.
- Keep repository guidance focused on non-obvious constraints and gotchas.
- Use high-fidelity references such as code, tests, artifacts, and rubrics when available.
- Keep durable memory separate from repository instruction files.
- Avoid repeating the same rule in the system prompt, project guidance, skill instructions, and tool description.

For Liminal, prompt quality is therefore not measured by instruction volume. It is measured by whether the right context is available, with clear provenance and authority, at the moment it is useful.

## Architectural decisions

### 1. Session state is semantic, not provider-shaped

The durable session model should consist of typed semantic entries rather than a flat vector of provider roles. A possible shape is:

```text
SessionEntry
  id
  parent_id
  timestamp
  agent_instance_id
  payload:
    UserMessage
    AgentOutput
    ToolCall
    ToolResult
    ContextSummary
    ProviderOpaqueItem
    ControlEvent
```

Instructions do not need to be repeatedly copied into the conversational log. They are resolved from an instruction stack for each context view. A control event may record a profile or project-instruction change when reproducibility requires it.

Every entry has a parent. This makes the log tree-ready without requiring a separate branch implementation. A normal linear session simply has one child per entry.

### 2. Provider roles remain an adapter vocabulary

`provider::Role` may remain temporarily, but only in the request-building boundary. New session and agent APIs should not use it as their domain model.

The provider-neutral lowering rules are:

| Liminal semantic item          | OpenAI Responses                              | Anthropic Messages                            |
| ------------------------------ | --------------------------------------------- | --------------------------------------------- |
| Runtime instruction            | `system` or verified equivalent               | ordered block in top-level `system`           |
| Application/agent instruction  | `developer` item or top-level `instructions`  | ordered block in top-level `system`           |
| Trusted project instruction    | `developer` item with provenance              | ordered block in top-level `system`           |
| User task                      | `user` input message                          | `user` message                                |
| Agent-generated text           | `assistant` output message                    | `assistant` message                           |
| Tool invocation/result         | typed call/result items                       | typed tool-use/result blocks                  |
| Provider reasoning/compaction  | replay provider item exactly when required    | replay provider block exactly when required   |
| Retrieved or untrusted content | tool result or clearly delimited task context | tool result or clearly delimited task context |

Retrieved files, web pages, command output, and other untrusted data must never be promoted to developer instructions merely because they are useful context.

### 3. Instructions form a resolved stack

The context builder resolves instruction sources in a stable order:

1. Liminal runtime contract.
2. Agent profile instructions.
3. Environment and execution constraints.
4. Project instructions from repository root toward the working directory.
5. Task-local policy selected by an explicit workflow or skill.

Each source carries:

- authority;
- origin and path or identifier;
- trust classification;
- applicable scope;
- content hash or version; and
- estimated token cost.

Resolution must deduplicate identical content and report conflicting sources. It should not silently solve conflicts by repeating the higher-priority rule multiple times.

The initial runtime prompt should be small. Tool-specific instructions belong in tool definitions. Large, specialized procedures should be loaded on demand. Repository instructions should describe constraints the model cannot reliably infer from the repository itself.

### 4. Every request uses a context builder

The request pipeline is:

```text
agent profile + runtime + project guidance
                    |
session branch --> context builder <-- selected skills/references/tools
                    |
          bounded semantic context view
                    |
              provider adapter
                    |
                API request
```

The context builder should:

1. Resolve the agent profile and instruction stack.
2. Select the active session branch.
3. Preserve atomic groups such as a tool call and its result.
4. Include provider-native continuation items only when compatible.
5. Select relevant on-demand references and memory.
6. Estimate input tokens using model metadata.
7. Reserve space for output, reasoning, and tool continuation.
8. Compact older context when the budget would be exceeded.
9. Emit an inspectable manifest before provider lowering.

The resulting manifest should make debugging questions answerable: which instruction won, why a file was loaded, what was summarized, and why an older item was omitted.

### 5. The session log is append-only and branchable

Edits, retries, model switches, and future agent delegation should create new descendants instead of mutating earlier entries. The session stores the current leaf separately.

Benefits include:

- safe retry and rewind;
- auditable compaction;
- cheap alternate branches;
- future child-agent branches; and
- reproducible context construction.

Provider-native opaque items carry provider and model-family provenance. They may be replayed only when the target adapter declares them compatible. Switching providers drops incompatible opaque items from the context view without deleting them from the session log.

### 6. Compaction is an explicit context operation

Liminal should compact before requests exceed the usable model window. The budget is:

```text
usable input = context window
             - reserved output
             - reserved reasoning/tool continuation
             - safety margin
```

Compaction creates a typed `ContextSummary`; it does not replace or rewrite the original entries. A summary should contain structured sections such as:

- user goal and decisions;
- completed work;
- current state;
- files and symbols involved;
- tool and test results;
- unresolved questions; and
- next actions.

Canonical runtime, agent, and project instructions remain outside the summary and are resolved afresh. A summary must not be allowed to elevate quoted user content or tool output into instructions.

The recent window should preserve complete turns and atomic tool groups. If provider-native compaction is available, its item is stored with provenance and replayed only on a compatible path. A visible provider-neutral summary is still needed for provider switching and session inspection.

### 7. Agent profiles and instances are separate

An `AgentProfile` should eventually contain:

```text
AgentProfile
  id
  name
  description
  instructions
  model preferences
  reasoning preferences
  tool policy
  context policy
  compaction policy
```

An `AgentInstance` should contain:

```text
AgentInstance
  id
  profile_id
  session_id
  branch_leaf_id
  parent_agent_instance_id?  // absent for the root agent
  status
  effective permissions
```

The root/main agent uses the same type and execution loop as a future child agent. Its special properties are that it has no parent, owns the user-facing branch, and receives the user's input directly.

A future child instance must inherit the intersection of its parent's permissions and its profile policy. It cannot gain tools or permissions through its prompt. Delegation should pass an explicit task packet and selected context, not clone the parent's entire context by default.

This data model should be introduced before orchestration, but no spawning, scheduling, or supervision system is required now.

### 8. Trust and authority remain distinct from relevance

Relevant content is not automatically trusted instruction. The builder must distinguish:

- Liminal-owned instructions;
- trusted project instructions;
- user requests;
- model output;
- tool output;
- retrieved documents; and
- provider-private state.

Tool output and retrieved documents should be presented as data through tool-result or task-context channels. Embedded instructions inside that data do not acquire developer authority. Repository instruction files are treated as project instructions only when the workspace itself is trusted.

## Proposed component boundaries

The following boundaries are conceptual; exact C++ names may change during implementation.

```text
agent/
  AgentProfile
  AgentInstance
  AgentRuntime

session/
  Session
  SessionEntry
  SessionStore
  BranchCursor

context/
  InstructionSource
  InstructionResolver
  ContextPolicy
  ContextBuilder
  ContextManifest
  Compactor
  TokenBudget

provider/
  Provider
  ModelCapabilities
  RequestProjection
  OpenAIProjection
  AnthropicProjection
```

`AgentRuntime` coordinates one model/tool loop. `ContextBuilder` decides what semantic material is included. A provider projection decides only how that material is represented on the wire. Provider adapters must not independently rediscover project instructions, compact arbitrary history, or redefine instruction precedence.

## Delivery phases

### Phase 1: Clarify roles and introduce context manifests

- Rename ambiguous uses of “role” in agent-facing APIs to “profile” or “message role.”
- Keep generated model output mapped to `assistant` for both providers.
- Keep OpenAI agent and project instructions mapped to `developer`.
- Add tests that prevent generated output from being serialized as `developer`.
- Introduce instruction provenance and a request context manifest.
- Centralize current request construction behind a context builder without adding persistence.

### Phase 2: Add a semantic session log

- Replace the flat provider-shaped history as the source of truth.
- Add typed entries, parent IDs, session IDs, and an active leaf.
- Lower semantic entries into the existing provider history representation at the adapter boundary.
- Preserve exact provider-native items with compatibility metadata.
- Add durable session storage and recovery.

### Phase 3: Add context budgets and automatic compaction

- Extend model metadata with context limits and capability flags.
- Track actual provider usage and estimated next-request cost.
- Reserve output and tool-continuation capacity.
- Add structured summaries and an automatic compaction threshold.
- Add context inspection so users can see what was included or summarized.

### Phase 4: Add agent profiles

- Move the current built-in coding prompt into a named profile.
- Add profile-level model, tools, instructions, and context policy.
- Instantiate the main/root agent through the shared `AgentInstance` model.
- Keep profile configuration independent of session history.

### Phase 5: Leave a deliberate extension point for child agents

- Add no child-agent execution until a concrete workflow requires it.
- When needed, add task packets, permission intersection, isolated branches, result summaries, cancellation, and bounded concurrency.
- Merge a child result as a typed entry or artifact reference, not by copying the child's whole transcript into the parent.

## Required invariants

- Model-generated conversation text is always lowered as `assistant`, never as `developer`.
- Agent-profile instructions are never stored as assistant output.
- A user message, tool result, retrieved document, or summary cannot acquire instruction authority through compaction or replay.
- Canonical instructions are resolved independently of conversational compaction.
- Context construction never mutates or deletes the source session log.
- Tool calls and their results are retained or omitted as atomic protocol-valid groups.
- Provider-native opaque items are replayed only to declared compatible providers and model families.
- The root agent and future child agents share one instance type and execution loop.
- A child agent can never expand the effective permissions of its parent.

## Verification strategy

### Role conformance

- Assert that an OpenAI request contains application instructions as developer-level guidance, user input as `user`, and replayed model text as `assistant`.
- Assert that an Anthropic request puts resolved instructions in the system channel and preserves alternating user/assistant conversation semantics.
- Assert that no code path serializes generated agent output as a developer instruction.

### Context construction

- Snapshot a context manifest with multiple instruction sources and verify deterministic ordering, provenance, and deduplication.
- Verify that nested project instructions apply only within their path scope.
- Verify that tool output containing instruction-like text remains data.
- Verify that complete tool call/result groups survive recent-window trimming.

### Compaction

- Verify that summaries retain decisions, file state, tests, and unresolved work.
- Verify that canonical instructions remain outside summaries.
- Verify repeated compaction uses the previous summary plus newly compacted entries without losing recent turns.
- Verify that switching providers retains visible semantic history while dropping incompatible opaque items.

### Agent instances

- Verify the root instance has no parent and otherwise follows the common runtime path.
- Verify profile changes do not rewrite existing session entries.
- Before child execution is implemented, verify that the data model permits a parent ID and isolated branch without changing root behavior.
